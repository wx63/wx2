3. **先修 S4 再补测试**：api.test.js 缺 `});` 导致后续测试被嵌套吞掉，不先修则新测试白写。排为执行第 0 步。

## 一、现状诊断：为什么"用不上 Agent 能力"

代码走查结论（index.js `executeAgentCommand` / `buildAgentPlan`）：

1. **工具选择是规则不是模型决策**：`buildAgentPlan()` 全是 `if (lower.includes('尺码'|'退换货'|...))` 硬编码，模型无权决定调用链。
2. **步骤间零数据传递**：`research` 输出不会喂给 `listing`，各工具是孤立的一次 `chat/completions` 调用，最后 `outputs.join('---')` 拼接。
3. **无任何 Agent 机制**：无 tool-calling 循环、无 subagent（`sessions_spawn` 未用）、无记忆反馈。
4. **bridge.js system prompt 甚至禁止模型调用工具**（"不要调用搜索或网页抓取工具，用你已有的知识回答即可"）。

本质：**带模板的多次串行 LLM 问答（pipeline），不是 agent**。这是当初"快路径直连保速度"的工程取舍，MVP 可接受，但限制了系统天花板。

---

## 二、改造目标

1. 模型**自主规划工具链**（function calling），步骤动态生成而非模板生成
2. 步骤间**真实传递数据**（上一步输出 = 下一步输入）
3. 兼容现有前端与数据表（agent_runs / agent_steps 结构不变）
4. 保留审批闸门、失败兜底、速度优先原则

---

## 三、总体设计

```
指令
 │
 ▼
┌─────────────────────────────────────────────┐
│ runAgenticLoop()  ← 新增，替代规则管道       │
│                                             │
│  1. 直连 DeepSeek，携带 tools 定义           │
│     （kb_search / research / listing /      │
│       compliance / approval_draft ...）      │
│  2. 模型返回 tool_calls → 逐个执行本地工具    │
│  3. 工具结果作为 tool 消息喂回 → 模型继续     │
│  4. 直到无 tool_calls 或达最大轮数(8)        │
│  5. 每次工具调用 = 一条 agent_step 落库      │
└─────────────────────────────────────────────┘
 │
 ├─ 成功 → 正常输出（含审批草稿则进闸门）
 └─ 失败（模型不支持 tools / 超时 / JSON 坏）
       → 回退现有 buildAgentPlan 规则管道
```

### 设计原则

- **混合模式**：`AGENT_MODE=agentic|rules|auto`（默认 auto：检测到模型支持 tools 就用 agentic，否则 rules）
- **规则兜底保安全**：`detectAction()` 审批闸门保持关键词兜底——即使模型漏调 `approval_draft`，命中动作规则的指令最终输出仍强制进审批草稿
- **知识库预注入**：`wantsKb` 类关键词命中时，先本地 `retrieve()` 把结果注入首轮 system 上下文，省一次模型工具调用（保速度）
- **可观测**：每轮 tool_call 的 args 与 output 都落库，前端现有步骤展示直接复用

## 四、改动明细

### 4.1 server/bridge.js —— 新增 tool-calling 直连方法

```js
/**
 * runAgentTools：带工具循环的直连调用（快路径）
 * @param {string} prompt      用户指令
 * @param {Array}  tools       OpenAI 风格 tools 定义
 * @param {object} opts        { maxRounds=8, onStep(toolCall, result), sessionId }
 * @returns {Promise<{ok, content, steps:[{tool,args,output}], raw, error}>}
 *
 * 实现要点：
 * 1. body.messages = [{role:'system',...}, {role:'user',content:prompt}]
 * 2. body.tools = tools；body.tool_choice = 'auto'
 * 3. 循环：解析 choices[0].message
 *    - 有 tool_calls → 逐个执行本地工具（由 index.js 注入 executor），
 *      把 {role:'tool', tool_call_id, content} 追加进 messages
 *    - 无 tool_calls → 结束，取 message.content
 * 4. 每轮走一次 onStep 回调（index.js 用它落库 agent_steps）
 * 5. 解析容错：tool_call JSON 参数解析失败 → 重试一次；仍失败则回退
 * 6. 超时：沿用 DIRECT_TIMEOUT_MS 按轮计算，总超时 = 轮数 × 超时
 */
```

关键点：
- 复用现有 `PROVIDER` 配置（baseUrl/apiKey 已就绪，DeepSeek 官方支持 function calling）
- `max_tokens` 从 2000 提到 4000（多步场景输出更长）
- **不改** `runAgent()` 现有签名，`runAgentTools()` 作为新导出，规则管道原样保留

## 六、验收标准

1. **动态步骤链**：指令"调研露营椅竞品，写个 listing，再合规审查"→ 模型自主产出 `research → listing → compliance` 真实步骤链（非模板），前端正常展示
2. **数据传递**：listing 输出能引用 research 结论（如价格带、卖点词）
3. **审批闸门不破**："发个推广帖"仍产出审批草稿（模型调用 + 规则双保险）
4. **知识库优先**："这件衣服有 XL 吗" → 本地检索命中，单步 7-17s 内完成
5. **回退有效**：AGENT_MODE=rules 时与改造前输出一致；直连失败仍兜底 Gateway
6. **测试全绿**：现有 18 项 + 新增 tool-calling 成功路径测试

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| DeepSeek tool calling 偶发 JSON 参数非法 | 解析失败重试 1 次，仍失败回退规则管道 |
| 多步调用成本/耗时上升（3 步约 30-60s） | 知识库预注入省轮次；maxRounds 上限；前端已有轮询 |
| 模型漏调关键工具（如忘查知识库） | 关键词预注入 + rules 兜底双保险 |
| 工具输出过长撑爆上下文 | 每轮 output 截断 20000（沿用 truncateText），tool 消息截断 4000 |
| 与飞书入口并发 | 沿用 enqueueCommand 队列（检测报告 S2 另案修） |
