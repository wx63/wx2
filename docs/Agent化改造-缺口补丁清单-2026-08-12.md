# Agent 化改造 —— 缺口补丁清单（给 Codex 执行）

> 日期：2026-08-12 · 来源：方案 v1.1 验收（对照 Agent化改造方案-2026-08-12.md）
> 现状：核心改造已落地（runAgentTools / TOOL_SCHEMAS / runAgenticCommand / AGENT_MODE / S2 飞书 / S4 测试），20 项测试全过
> 本清单 = 验收时发现的 6 个未落实/半落实点，按优先级排序。改完跑 `npm test` 必须全绿。

---

## 缺口 1（最高优先，约 1 行）：agentic 回退不可观测

- **位置**：`server/index.js` → `executeAgentCommand()` 的规则管道分支（`buildAgentPlan` 执行段，`finishAgentRun` 调用处，约 L619/L635）
- **现状**：agentic 路径失败后 `stats.retries += 1` 并回退规则管道，但 `finishAgentRun` 的 `path` 恒为 `'agent'`，无法区分"正常规则执行"与"agentic 失败回退"
- **要求**：回退发生时 `path` 记为 `'agentic_fallback'`，正常规则执行保持 `'agent'`。成功与失败两条 finishAgentRun 分支都要处理（可先判断 `stats.retries > 0`）
- **验收**：`AGENT_MODE=agentic` 且直连失败时，agent_runs 记录 `path='agentic_fallback'`；`AGENT_MODE=rules` 时 `path='agent'`

## 缺口 2（最高优先）：审批双保险缺"强制补跑 approval_draft"

- **位置**：`server/index.js` → `runAgenticCommand()` 尾部（返回前）
- **现状**：`processCommandJob` 里 `detectAction()` 命中时用 `draft: result.content` 直接建审批，但 agentic 路径**不保证**模型调用了 `approval_draft` 工具——模型可能直接输出裸文案，审批草稿就没有"目标平台/内容草稿/风险提示/人工确认项"结构
- **要求**：`runAgenticCommand()` 返回前判断：`detectAction(command)` 命中 **且** `result.steps` 中没有 `approval_draft` 步骤 → **强制补跑一次** `approval_draft` 工具（复用 `agenticExecutor('approval_draft', { task: command })`），把其输出作为最终 `content`（或追加到 content），并补一条 agent_step（tool:'approval_draft', meta: { agentic: true, forced: true }）
- **验收**：指令"发个推广帖，内容写露营椅促销"→ 即使模型第一轮没调 approval_draft，最终审批草稿仍是结构化方案（含目标平台/风险提示/人工确认项），agent_steps 含 forced 标记步骤

## 缺口 3（高优先）：前端详情页仍显示模拟步骤

- **位置**：`public/app.js` → `buildSteps()`（约 L71）及命令详情渲染处（`consoleState.steps` 消费处）
- **现状**：`buildSteps()` 在拿不到真实步骤时生成写死的"运营总监路由 → 拉起 XX Agent → 执行 → 审批闸门 → 产出"动画。后端已落真实 agent_steps，但详情页可能仍显示模拟
- **要求**：详情页**优先渲染后端真实步骤**（`/api/commands/:id/run` 返回的 `agentRun.steps`，含 `seq/kind/label/tool/status/output`），仅当后端无步骤数据时才回退 `buildSteps()` 模拟。模拟分支可保留但必须降级
- **验收**：下达一条多步指令，详情页显示的是后端真实步骤（含工具名、状态、输出），不是写死动画；后端无步骤时仍能显示模拟

## 缺口 4（中优先）：工具定义双源并存

- **位置**：`server/index.js` → `AGENT_TOOLS`（约 L289）与 `TOOL_SCHEMAS`（约 L434）
- **现状**：规则管道用 `AGENT_TOOLS` + `buildToolPrompt`，agentic 用 `TOOL_SCHEMAS` + `agenticExecutor`，两套定义并行，加工具要改两处，易不一致
- **要求**：合并为**单一数据源**：每个工具一条定义 `{ name, label, description, schema, executor, prompt }`（prompt 可复用现有 buildToolPrompt 模板），`TOOL_SCHEMAS` 由它生成（map 出 OpenAI 格式），`agenticExecutor` 由它注册。规则管道保持行为不变
- **验收**：加一个工具只改一处；`npm test` 全绿；rules 模式输出与改前一致

## 缺口 5（中优先）：上下文只截断不裁剪，多轮有爆窗风险

- **位置**：`server/bridge.js` → `runAgentTools()` 循环
- **现状**：每轮工具输出截断 4000 已做，但 `messages` 全量累积（assistant tool_calls + tool 结果都 push），maxRounds=8 时最坏 64K+ 输出，逼近 DeepSeek 128K 上限
- **要求**：加**历史窗口管理**：
  - `AGENT_MAX_ROUNDS` 默认降到 `6`（`.env.example` 同步）
  - 只保留最近 **4 轮**的完整 tool 消息；更早轮次的 tool 结果截断到 **500 字符**（保留 `tool_call_id` 对应关系）
  - 实现为 `runAgentTools` 内部维护消息数组的压缩函数，不影响 onStep 落库
- **验收**：maxRounds=8 的极端场景下 messages 总长度有界；功能无回归

## 缺口 6（低优先）：max_tokens 硬编码

- **位置**：`server/bridge.js` → `runAgentTools()` 的 body 构造（`max_tokens: 4000`）
- **要求**：改为环境变量 `OPENCLAW_DIRECT_MAX_TOKENS`（默认 4000），`.env.example` 补注释说明影响成本
- **验收**：设 `OPENCLAW_DIRECT_MAX_TOKENS=8000` 后生效

## 缺口 7（最高优先，回归 bug）：agenticExecutor 已删，runAgenticCommand 仍引用

- **位置**：`server/index.js` → `runAgenticCommand()` 两处（L479 executor 箭头函数、L495 强制补跑 approval_draft）
- **背景**：重构 AGENT_TOOL_DEFS 单一数据源时删除了独立函数 `agenticExecutor`（逻辑已并入 `AGENT_TOOL_DEFS[].handler`），但这两处引用未同步，运行时 ReferenceError（实测：工具步骤全部 `ERROR: agenticExecutor is not defined`，模型被迫自问自答，且因 runAgentTools 返回 ok:true 被当作成功）
- **修复**：
  ```js
  // L479 改为
  executor: async (name, args) => {
    const def = AGENT_TOOL_DEFS.find(d => d.name === name);
    if (!def) return { output: `未知工具 ${name}` };
    return def.handler(args, meta);
  },
  // L495 改为
  const def = AGENT_TOOL_DEFS.find(d => d.name === 'approval_draft');
  const forced = def ? await def.handler({ task: command }, meta) : { output: '' };
  ```
- **验收**：实测多步指令（如"调研露营椅竞品，写一个listing，再合规审查"），DB agent_steps 的 research/kb_search/compliance 状态为 done 且有真实输出；再实测"发个推广帖"验证审批强制补跑

## 缺口 8（低优先，防御性）：工具全挂时不应当成功

- **位置**：`server/index.js` → `runAgenticCommand()`
- **现状**：runAgentTools 返回 ok:true 但所有工具步骤都 error 时（如上回归），被当作成功直接返回
- **要求**：若 `result.steps` 非空且全部 error，视为失败回退规则管道（`return { ok:false, error:'所有工具调用失败', _fallbackable:true }` 或直接走既有回退分支）
- **验收**：模拟 executor 全挂场景，确认回退到 rules 管道且 path 标记 agentic_fallback
