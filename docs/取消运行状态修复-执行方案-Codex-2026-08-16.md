# 修复：取消运行是"表面取消"（状态回写覆盖）— 执行方案（Codex）

> 依据：《测试报告-2026-08-16.md》§6.1（影响轻微，但建议修复）
> 目标：用户取消的运行保持 `cancelled` 状态，不被底层调用返回后覆盖回 `ok`。

## 根因（代码位置）

- `server/db.js:729` `finishAgentRun(runId, r)`：`UPDATE agent_runs SET status = @status ...` **无条件覆盖**状态
- `server/db.js:789` `markAgentRunCancelled(runId, userId, reason)`：仅当 `status IN ('queued','running')` 时置 `cancelled` ✓
- 时序问题：
  1. 用户点取消 → `markAgentRunCancelled` → 状态 `cancelled`
  2. 但底层模型调用仍在 await（`runAgenticCommand` / `runPlannedStep`）
  3. 调用返回后，调用方执行 `finishAgentRun(runId, {status:'ok'...})`（`index.js:379/477/492`）→ **状态被覆盖回 `ok`**
- 三个调用点（agentic 成功、plan 成功、plan 失败）全部走 `finishAgentRun`，**单点修复即可覆盖所有路径**

## 修复方案

### 改 `server/db.js` 的 `finishAgentRun`（唯一改动点）

把 UPDATE 的 `status = @status` 改为**条件保留 cancelled**：

```js
function finishAgentRun(runId, r) {
  const ts = nowIso();
  db.prepare(`UPDATE agent_runs SET
    status = CASE WHEN status = 'cancelled' THEN 'cancelled' ELSE @status END,
    model = @model,
    path = @path,
    duration_ms = @durationMs,
    plan_json = @plan,
    result = @result,
    error = @error,
    summary = @summary,
    context_json = @context,
    stats_json = @stats,
    updated_at = @ts,
    finished_at = @ts
    WHERE id = @id`).run({ ... });
  return getAgentRun(runId);
}
```

行为：
- 已被取消的运行 → 状态**保持 `cancelled`**，但 result/summary/stats 等结果字段**照常写入**（方便事后查看真实产出）
- 正常任务 → 行为不变（`ok` / `error`）
- 不需要额外 SELECT 查询（CASE WHEN 一行解决）

### 可选加固（建议一并做，2 行）

`markAgentRunCancelled` 目前仅 `queued/running` 生效；`finishAgentRun` 修复后已足够，**无需改**。

## 测试更新（server/test/e2e-live.test.js）

现有用例"取消进行中运行（mock 挂起模型响应）→ cancelled"**断言不变**（取消瞬间仍是 cancelled）。
**新增/调整断言**：释放挂起响应、等待约 1500ms 后，复读该 run：
- `status` 仍为 `cancelled`（核心断言）
- `result` 字段可非空（结果已落库，不丢数据）——如实现简单可断言，否则仅断言 status

> 若原用例已包含"释放后复读为 ok"的旧断言，删除/替换为上述新断言。

## 风险与回滚

- 风险：低。单点 SQL 修改，不涉及流程逻辑；仅影响"取消后"的状态回写
- 回滚：还原 `finishAgentRun` 的 status 行即可
- 不碰：`.env`、`data/`、审批/订单/知识库逻辑、前端

## 不做什么

- 不实现"真取消"（AbortController 注入终止模型调用）——改动面大、收益低，本期不做
- 不改前端按钮行为
- 不改 SSE 事件逻辑
