## 二、严重问题（🔴 优先处理）

### S1. 授权越权——多个接口返回跨用户/跨角色数据（IDOR）

| 接口 | 缺陷 |
|---|---|
| `GET /api/agent-runs`（index.js:901） | `requireAuth` 即可，**列出所有用户的全部运行记录**（含指令内容） |
| `GET /api/approvals`（index.js:938） | 任何登录用户（**含 viewer**）可读**全部审批草稿**（对外动作内容=敏感经营信息） |
| `GET /api/integrations/feishu`（index.js:886） | 任何登录用户可读**最近 20 条飞书消息**（chatId、senderId、消息全文=客户 PII） |
| `GET /api/dashboard`（db.js getDashboard） | 返回 `listLeads('all')`——**全部线索（客户 PII）给所有登录用户** |

现有权限测试（api.test.js:97-108）只测了 `viewer 不能 POST 报告`、`operator 不能读命令`，**恰好没测 viewer 能否读 approvals / agent-runs / feishu**——漏洞被测试盲区掩盖。

**方案**：DB 层所有 list 函数加 `WHERE user_id = ?`（或按角色）：admin 全量，operator 看自己的，viewer 只读脱敏统计；feishu 状态接口把 `recentMessages` 从响应里移除或截断为 `{count}`；dashboard 对非 admin 返回聚合指标而非原始线索。

### S2. Feishu 消息直通执行，绕过整个命令队列（index.js:973）

```js
const result = await executeAgentCommand({   // ← 直调，没有 enqueueCommand
```

- 绕过：并发上限（`COMMAND_CONCURRENCY=1`）、命令限流（10/10min）、队列持久化
- **风险**：飞书群任何能发消息的人，每条消息=一次 LLM 调用+一次 agent 编排（成本放大器）；并发绕过队例上限后与页面指令并发写库（正好撞上 S3 的竞态）
- **方案**：Feishu handler 走同一个 `enqueueCommand`，并在 feishu 侧加每 chatId 限流（如 5/min）+ 消息长度上限

### S3. 报告 ID 竞态（db.js:906-921）

```js
const seq = Number(db.prepare('SELECT COUNT(*) FROM reports').get().n) + 1;  // 并发两会话算出同一 seq
const id = 'R-' + ...;
db.prepare('INSERT INTO reports ...').run({ id, ... });   // 第二个写入 → PRIMARY KEY 冲突 → 500
```

两条路径可同时触发：网页 `/api/reports` + Feishu 消息（若 S2 修好后仍如此）→ 真实并发窗口。**方案**：改 `id INTEGER PRIMARY KEY AUTOINCREMENT` 让数据库分配，或事务内 `INSERT OR IGNORE` + 重试。

### S4. 测试文件结构损坏（api.test.js:173-267）

第 173 行 `test('csv export requires auth...', async () => {` **缺一个 `});`**，导致第 184-266 行**所有后续测试被嵌套为该测试的子测试**。虽然 18 项全"通过"（Node 会跑嵌套子测试），但：

- 断言计数/失败定位全乱，将来 184 行以后的测试失败会报成"csv export 失败"
- 这是"测试全绿"但覆盖有效性存疑的典型信号

**方案**：在 181 行后补 `});`，并加一条"运行 `node --test` 检查输出无异常嵌套"的 CI 断言。

## 三、中等问题（🟠）

### M1. `/api/health` 未鉴权，泄露内网地址（index.js:618-629）

注册在 `requireAuth`（668 行）**之前**，未登录可访问，返回 `providerBaseUrl`、`gatewayUrl`。前端还把它渲染到侧边栏。**方案**：移到鉴权后，或仅返回 `{online:true, version}`。

### M2. 登录时序攻击 + 用户枚举（index.js:640-643）

邮箱不存在时**直接跳过 bcrypt 比较**（省几十 ms）→ 可枚举注册邮箱 + 计时侧信道。**方案**：用固定假哈希对不存在用户也跑一次 bcrypt 比较，再统一返回 401。

### M3. CSP 关闭（helmet `contentSecurityPolicy: false`）

前端有 `escapeHtml` 兜底，但 CSP 是第二道防线（防"漏转义时"内联脚本注入）。**方案**：启用默认 CSP 并放宽 `'unsafe-inline'` 于样式即可，脚本全外链（现有 index.html 无内联 script，可直接开）。

### M4. 会话配置隐患（index.js:138-151）

- `rolling:true` → **每次请求都写会话表**（写放大，配合 sync DB 阻塞主线程）
- `secure:isProduction` → 非生产环境 cookie 走明文（本地可接受，上云前必须强制）
- **方案**：关 rolling 或改为只对未过期前半段续期；部署前置 `NODE_ENV=production` + 强随机 `SESSION_SECRET`（当前 `dev-change-me` 是占位）。

### M5. 前端静默吞错（app.js:875 / 1570 / 846-849）

- 保存报告 `.catch(() => {})`——失败无感知，刷新即丢
- 初始化 `catch {}`——后端宕机页面静默空白
- `refreshLeadsFromServer` 无 catch——网络失败被误标"转化成功"

**方案**：catch 内至少 `showToast`，区分 401/网络/业务错误。

### M6. 前端 30s 轮询与审批决策竞态（app.js:1665 vs 697-727）

轮询用新对象整体替换 `APPROVALS` 数组，`decideApproval` 用记录的下标回写——请求往返期间数组被替换则写错槽位/丢 `_deciding`，可重复点击。**方案**：决策完成后按 `id` 重新定位写入；轮询改用合并而非整体替换。

### M7. 知识库每次查询重载文件（kb.js `retrieve()`）

`loadKnowledgeBase()` 在**每个请求路径上同步读盘**。**方案**：启动时加载+文件 mtime 缓存，或加 5 分钟 TTL。

### M8. 无 `busy_timeout` + 全同步 DB（db.js:13-14）

只有 WAL + foreign_keys，没有 `PRAGMA busy_timeout`；`DatabaseSync` 所有操作阻塞主线程。WAL 下并发写（页面+飞书）会直接 `SQLITE_BUSY` 500。**方案**：加 `busy_timeout=5000`；读写重操作移出请求路径或后续迁 better-sqlite3 异步 worker。

### M9. 混合时间戳格式（db.js）

部分列用 `datetime('now')`（空格分隔 UTC），部分用 `toISOString()`（T+Z）——排序/展示/导出不一致。**方案**：统一 `new Date().toISOString()` 存 ISO-8601。
