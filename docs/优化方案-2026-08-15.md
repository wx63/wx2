## P1 · 性能优化(当前最痛点:业务指令 21-27s)

### 1.1 直连路径改为流式输出(SSE)

- **现状**:`server/bridge.js` 三处 `stream: false`(行 123、173、255),前端要等完整结果 21-27s。
- **目标**:直连 provider 时 `stream: true`,后端转发为 `text/event-stream`,前端打字机展示。
- **任务**:
  1. `server/bridge.js` 新增 `runDirectStream()`:POST `{baseUrl}/chat/completions` 带 `stream: true`、`Buffer.from(body,'utf8')` 编码(沿用中文修复),SSE 解析按 `data:` 行切分,聚合增量内容;
  2. `server/index.js` 指令接口(查 `/api/command` 路由)在直连路径下返回 `Content-Type: text/event-stream`;失败/超时自动回退到旧的完整 JSON(非流式)响应,保持接口兼容;
  3. 前端 `public/app.js` 对应指令面板用 `fetch` + `ReadableStream` 解析 SSE,边收边渲染;保留旧的 await 逻辑作回退;
  4. 注意:流式下 `max_tokens`、`tool_choice` 仍须保留;工具调用场景(price_lookup 等)若模型中途要调工具,SSE 会先出 tool_call 增量 —— 稳妥做法:仅对"纯对话/生成"指令走流式,工具类指令仍走非流式。
- **验证**:
  - 浏览器发一条指令,打字机效果出现且首 token < 3s;
  - 工具类指令(查价)仍能正常触发 price_lookup;
  - 断网/超时回退后前端仍有完整结果可看。

### 1.2 DeepSeek Prompt 缓存

- **现状**:`server/bridge.js` 每次把系统提示词 + KB 检索块拼入 messages 发全量,直连 cost 为全价。
- **任务**:
  1. 系统提示词固定前缀保持稳定(不要每次插入时间戳/随机变量),让 DeepSeek 的 context caching 命中;
  2. 可调参数:`OPENCLAW_DIRECT_MODEL` 换用支持缓存的模型或在 messages 首条加 `"cache_control"` 标注(DeepSeek 官方 API 以自动缓存为主,验证后决定是否需要显式控制);
  3. 在 `server/index.js` 日志里补 `usage.prompt_cache_hit_tokens` 字段落库,便于观测命中率。
- **验证**:连续发两条相同系统前缀的指令,第二条 `prompt_cache_hit_tokens > 0` 且耗时下降。

### 1.3 SQLite 索引(数据量增长防慢)

- **现状**:`audit_logs`(112 行)、`activity_feed`(45)、`agent_steps`(51)、`commands`(30)按时间查询频繁,无时间索引。
- **任务**:在 `server/db.js` 建表后补索引:
  - `CREATE INDEX IF NOT EXISTS idx_audit_createdAt ON audit_logs(createdAt);`
  - `CREATE INDEX IF NOT EXISTS idx_feed_createdAt ON activity_feed(createdAt);`
  - `CREATE INDEX IF NOT EXISTS idx_steps_runId ON agent_steps(agent_run_id);`
  - `CREATE INDEX IF NOT EXISTS idx_commands_createdAt ON commands(createdAt);`
- **验证**:`EXPLAIN QUERY PLAN` 查上述表时间列出现 `USING INDEX`;重启后 23/23 测试仍绿。

### 1.4 KB 检索参数复核

- **现状**:`server/kb.js` 已按 top-k 截断(`.slice(0, k)`),检索有上限。
- **任务**:检查 `k` 与每块字数,确认单次问答进 prompt 的知识块 ≤ 5 块、总量可控;若某次检索拼入过多块导致慢,调小 k 并配合 P1.2 缓存。
- **验证**:`/api/kb/query` 一次问答的 prompt token 数稳定在可接受范围。

- **验证**:重启后端后 `pm2 status` 为 online;任务管理器里 node 进程存在。

## P4 · 业务闭环(系统价值核心)

### 4.1 Orders 闭环:审批"批准并归档"→"批准并执行"

- **现状**:`orders` 表 0 行;审批中心批准后只落库不真发帖/下单(README FAQ 已注明)。
- **前提**:需要至少一个外部平台的 API 凭据(微信/WhatsApp/IG/X/ERP)。取得后:
  1. `server/` 新增 `platforms/` 目录,每平台一个适配器(`wechat.js`、`instagram.js`...),统一接口 `publish(post)` / `createOrder(order)`;
  2. 审批"批准"按钮联动适配器真执行,执行结果回写 `orders` / `approvals.status`;
  3. 失败重试 + 审计留痕。
- **未取得凭据前**:保持现状,不造假执行。

### 4.2 查价源加固

- **现状**:`server/price-lookup.js` 依赖慢慢买公开页 + 苹果官网 + 汽车之家,页面改版即失效。
- **任务**:
  1. 加 30 分钟内存缓存(key=商品关键词),同类查询不重复抓取;
  2. 每个源独立 try/catch,单源失败降级到下一源,绝不整体报错;
  3. 源返回结构变化时给出可读错误而非裸异常。
- **验证**:连续两次查同一商品,第二次命中缓存且耗时显著下降;手动断掉第一个源,仍能出结果。
