## 2. 测试方法与基线（重要）

### 2.1 为何不直接对线上库测试

初轮对**正在运行的线上服务**（PID 3872，`data/app.db`）直接测试时遇到关键陷阱：

- **WAL 多进程可见性问题**：`db.js` 打开连接时执行 `PRAGMA journal_mode=WAL`，外部进程对 `data/app.db` 的写入，**运行中的服务进程看不到**。用独立 Node 进程创建测试用户后，线上登录一律 401「邮箱或密码错误」（即便 bcrypt 比对本地为真）。这是旧报告多项 FAIL 的根因，属**测试方法问题而非产品缺陷**。
- 线上登录限流 5 次/15 分钟/IP，多账号轮番登录很快打满 429。

### 2.2 采用的权威基线

构建**进程内隔离测试夹具**，完全绕开上述问题：

- 临时库 `C:/tmp/*data` + `NODE_ENV=test`（限流×1000）+ 独立 PORT
- 同一进程 `require` index.js 与 db.js → **同一模块缓存 → 同一 DatabaseSync 连接** → 用户/数据即时可见
- 管理员由 `bootstrapAdminFromEnv` 创建；viewer/operator 用同一连接插入
- 线上实测仅用于：上传安全、CSRF、会话安全、功能冒烟（无 WAL 干扰的路径）

> 结论：**本报告缺陷全部基于隔离环境可复现的实测**，不依赖旧报告结论。

## 3. 缺陷清单（按严重度）

### 🔴 P1-1 订单 ID 复用 → 静默覆盖既有订单（数据丢失）

- **位置**：`server/db.js:967-971` `addOrder()`
- **现象（实测复现）**：
  1. 创建订单 A → `ORD-00001`
  2. 创建订单 B → `ORD-00002`
  3. 删除订单 A
  4. 再创建订单 C → 返回 `201`，`id=ORD-00002`，**订单 B 的记录被整行覆盖为订单 C**，无任何报错
- **根因**：`id = 'ORD-' + (COUNT(*)+1)` 用**现存行数**生成序号，删除后序号回退；且新订单用 `INSERT OR REPLACE` 落库，同 ID 直接替换。并发插入时两个请求算出同一 seq 同样静默覆盖。
- **影响**：删单后建单即丢数据，属**静默数据损坏**，业务系统不可接受。
- **修复建议**：
  - 改用自增 `INTEGER PRIMARY KEY AUTOINCREMENT`，或独立序列表（`UPDATE seq SET n=n+1` 原子推进）；
  - 新订单用普通 `INSERT`（ID 冲突抛错重试），不要把新建和覆盖混用 `INSERT OR REPLACE`；
  - `order_no` 建议加 UNIQUE 约束防重复单号。

### 🟠 P2-1 viewer 角色可读取全部订单数据（越权）

- **位置**：`server/index.js:894` `GET /api/orders`、`:902` `GET /api/orders/stats`
- **现象（实测）**：viewer 角色 GET `/api/orders` 与 `/api/orders/stats` 均返回 `200` 与全量订单数据。
- **对比**：leads / approvals / agent-runs / commands / command-POST / orders-POST / settings-PATCH / kb-upload 等对 viewer 全部正确返回 403。**订单读接口是唯一漏挂 `requireRole('operator','admin')` 的一处**。
- **影响**：最低权限角色可读到全量订单明细与统计（金额、客户、物流单号等敏感经营数据）。
- **修复建议**：两条 GET 路由补 `requireRole('operator', 'admin')`（与 POST 一致），并补一条 viewer 读取 403 的回归用例。

### 🟡 P2-2 全局错误处理把客户端错误一律压成 HTTP 500

- **位置**：`server/index.js:1248-1252`
- **现象（实测，两个触发面）**：
  - 畸形 JSON `{"orderNo": ` → body-parser 抛 `entity.parse.failed`（自带 `statusCode=400`）→ 实际返回 **500**
  - 超过 2MB 的 JSON body → body-parser 抛 `entity.too.large`（自带 `status=413`）→ 实际返回 **500**
- **根因**：错误处理器除 CORS 外对所有错误一视同仁返回 `500 内部错误`，无视 `err.status`/`err.statusCode`。
- **影响**：客户端语法错误被误报为服务端故障，污染监控/告警语义；超大请求不按 413 语义降级。
- **修复建议**：
  ```js
  app.use((err, req, res, next) => {
    if (err && err.message === 'CORS origin denied') return res.status(403)...
    const status = err.status || err.statusCode || 500;
    if (status >= 500) console.error('[server] error:', err);
    res.status(status).json({ ok: false, error: status >= 500 ? '内部错误' : err.type === 'entity.parse.failed' ? '请求体JSON格式错误' : '请求无效' });
  });
  ```
  并补畸形 JSON→400、超限 body→413 两条回归用例。

### 🟢 P3-1 订单状态字段无枚举校验

- **位置**：`server/db.js:983`（addOrder）、`:1009`（updateOrder）
- **现象（实测）**：POST `/api/orders` 传 `status:'not_a_status'` 返回 `201` 照单全收。
- **影响**：`orderStats()`（db.js:1023-1028）只统计 `pending`/`shipped`，非法状态订单计入 `total`/`today` 但不进任何状态桶 → **统计口径失真**；前端状态徽章渲染未知值。
- **修复建议**：入参白名单 `['pending','paid','shipped','delivered','cancelled']`（以业务实际状态机为准），非法值返回 400；统计改为按状态分组聚合，避免硬编码。

| 旧报告结论 | 纠正 |

| 因 WAL 多进程可见性导致的「测试账号建了登不进去」等 17 项 FAIL | 测试夹具问题，非产品缺陷，见 §2.1。 |

## 6. 遗留风险与运维建议

1. **WAL 多进程可见性（运维提示，非代码缺陷）**：对运行中服务做数据注入（建账号、导数据）必须走服务自身的接口，或重启服务让新连接看到落盘数据，否则出现「写入了但读不到」的假象。
2. **`orderStats` 硬编码状态桶**：与 P3-1 同源，建议聚合查询按 `status` 分组。
3. **错误日志敏感度**：畸形请求的原始 body 会被完整打印到服务日志（body-parser error 含 body 字段），日志落盘前建议脱敏。
4. **`addOrder` 的 `INSERT OR REPLACE` 行为**：除 ID 复用外，未来任何字段若新增 UNIQUE 约束，`REPLACE` 会先删后插，注意外键/审计字段副作用。
