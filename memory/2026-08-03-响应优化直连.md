# 2026-08-03 · 响应慢优化：绕过 Gateway 直连模型

## 背景
用户反馈"90s 太慢，正常用户谁等 90s"。前一轮把超时 60→90s、重试 1→2 次只是兜住不报错，没解决慢。

## 根因再深挖
业务题经 OpenClaw Gateway（`openclaw/main`）要 26-56s、~40% 失败（`non_deliverable_terminal_turn`）。两层原因：
1. **main agent 16k 上下文开销**：Gateway 路径 prompt_tokens=16174（系统注入的 agent 身份/技能/workspace 摘要），直连 provider 同一题只要几百 token。
2. **reasoning 模型**：deepseek-v4-flash `reasoning:true`，每次先思考再输出，偶发 thinking 跑飞耗尽 token 不产正文。

## 优化方案：快路径直连 + 慢路径兜底
- **快路径**：bridge.js 直连 shuyanai provider 的 `qwen3.6-flash`（`reasoning:false`），绕过 Gateway。实测 11-17s、5/5 成功。
- **慢路径兜底**：直连网络/HTTP 5xx/超时才退回 Gateway（保留 agent 能力）。

## 改动（bridge.js，重构）
- 新增 `runDirect()`：直连 `{baseUrl}/chat/completions`，model 用 `DIRECT_MODEL`（默认 `shuyanai/qwen3.6-flash`），30s 超时，body 用 `Buffer.from(...,'utf8')`（沿用上周中文修复）。
- 新增 `readProviderConfig()`：从 `~/.openclaw/agents/main/agent/models.json` 读 shuyanai 的 baseUrl/apiKey；env 可覆盖。
- 原 `runAgent()` 拆为 `runViaGateway()`（慢路径，60s 超时，占位文重试 1 次）。
- 新 `runAgent()` = `runDirect()` → 失败且 `_fallbackable` → `runViaGateway()`。
- 配置全可 env 覆盖：`OPENCLAW_DIRECT_MODEL` / `OPENCLAW_DIRECT_TIMEOUT_MS` / `OPENCLAW_GATEWAY_TIMEOUT_MS` / `OPENCLAW_PROVIDER_BASE_URL` / `OPENCLAW_PROVIDER_API_KEY`。

## 验证
| 场景 | 优化前(Gateway) | 优化后(直连) |
|---|---|---|
| 业务题×5 | 22-111s，2/5 失败 | **21-27s，5/5 成功** |
| 简单题 1+1 | 4-7s | 4.0s |
| 发帖审批 | - | 18.7s，触发审批闸门 ✓ |
| RAG 知识库问答 | - | 12s，带来源引用 ✓ |

业务题从最慢 111s → 稳定 21-27s，失败率 ~40% → 0。

## 权衡
- 直连绕过了 OpenClaw 的 agent 能力（技能调度、workspace 上下文、工具调用）。当前用法（运营指令执行/内容生成）不需要这些，反而因省了 16k 上下文而更快更稳。若后续需要 agent 工具能力，走慢路径兜底仍可触发。
- `qwen3.6-flash` 是非 reasoning 模型，复杂推理题质量可能弱于 deepseek-v4-flash；运营场景多为生成/分析类，够用。
